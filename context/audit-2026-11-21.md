## A. Executive summary

FinFlow is a single-page React 19 + Vite 7 app in plain JavaScript (no TypeScript) with a Supabase backend. It handles personal finances in PHP (Philippine pesos): income and expense tracking, a monthly dashboard, private receipt uploads, and a warranty tracker linked to receipts.

The code is careful about security and correctness. Money is calculated in whole cents, ownership is checked on every query, uploaded files can only be opened through 60-second signed links, and there are guards against a slow response landing in the wrong account after a user switch.

It's an MVP, not a finished product:
- The backend isn't reproducible from the repo.
- The budget feature only reads data and has no way to create a budget.
- There's no routing, linting or password reset.
- The code is written in a dense, minified one-line style that is hard to maintain.

## B. Technical architecture

```
index.html → src/main.jsx
  App() ── checks configuration (supabase.js) ── no keys → "Supabase key needed" screen
    │
    ├─ supabase.auth.getSession() + onAuthStateChange()
    │    each new login gets a fresh "account scope" (account-scope.js)
    │
    ├─ no session  → AuthScreen (sign in / sign up)
    └─ session     → AccountApp, remounted whenever the user changes
          ├─ data.js           → transactions, receipts, monthly_budgets tables + Storage bucket
          ├─ useWarranties.js  → warranty-data.js → warranties table
          ├─ transactions.js   → pure logic: validation, cents math, filters, totals
          ├─ warranties.js     → pure logic: date math, status, filtering
          └─ Views (tab state, no router): Dashboard · Transactions · Add Transaction ·
             Scan Receipt · Receipts · Warranties (Warranties.jsx) · Settings
```

- **Account scope** is the fix for the account-switch problem. Every login creates a scope object. On logout or user change, the old scope is invalidated before React draws anything. Every async action calls `scope.assert()` or `scope.current()` before updating the screen, so a late response from user A is thrown away once user B is signed in.
- **Security boundary:** the browser only ever has the publishable key. The real protection is Postgres row-level security (RLS) plus Storage policies. The `.eq('user_id', …)` filters in the frontend help correctness but aren't the security.
- **Build-time guard:** `scripts/public-env.mjs` runs before Vite starts. It allows only two `VITE_` variables and rejects anything that looks like a secret key or JWT.
- **Files:** 16 source files (~800 lines), 4 test files, 4 verification scripts, 1 migration, 5 docs. There was no `CLAUDE.md` at audit time.

## D. Design system

**Palette:** `src/tokens.css` defines all six approved colors with the exact hex values (Plum #302D42, Pearl #FAF9FC, Periwinkle #E1DDFF, Orchid #C7A6EC, Coral #FFB9B0, Violet #7859BE). Semantic tokens are built on top of them with `color-mix()`. No mismatches.

**Visual signature, as implemented:** four soft radial glows in `body::before`; a 12px dot texture in `body::after`, masked away from the center; glossy primary buttons (a gradient from #4B465F to Plum with an inset highlight); pill-shaped secondary buttons; a 2px lift on hover and a 0.98 press scale; a 240ms page entrance; support for reduced motion and forced-colors modes.

**Inconsistencies:**
1. Typography isn't editorial: `--font-heading` is the same as `--font-ui` (system sans).
2. Corner radii are mostly hardcoded: about 11 raw values (5–28px) despite three radius tokens.
3. Spacing is mixed: raw pixels in style.css and phase2.css, tokens in warranties.css. `h3` is hardcoded at 15px.
4. `backdrop-filter` on the opaque Plum sidebar has no visible effect. Only the banner uses `--surface-glass`.
5. The header month picker shows on tabs where it does nothing, and "+ Add transaction" shows on every page, including the Add Transaction page itself.
6. Mobile nav has six items, and Warranties is labelled "Cover".
7. Brand copy is inconsistent: "PRIVATE CLOUD FINANCE" vs "SECURE CLOUD MVP", plus "AI" in the logo.
8. There are no reusable components and no modals (it uses `window.confirm`).
9. Typo: "Loading your account?" (main.jsx line 68).

| `receipts` | Not in the repo | user_id, transaction_id → transactions, storage_path, merchant, receipt_date, total, suggested_category, extraction_status |

| `warranties` | Migration `20261104171802` | Section F |
| Storage `finflow-receipts` | Configured in the dashboard | Private bucket, 10 MB limit, JPEG/PNG/WEBP/PDF only. Policies restrict access by the user's ID folder (per the Codex audit). |

**Cascade behaviour:** deleting a user deletes their warranties, and deleting a receipt deletes its warranties. What happens to a receipt when its transaction is deleted is **unknown**. The UI says "Attached receipts remain", which is only true if `receipts.transaction_id` is set to `ON DELETE SET NULL`; with `NO ACTION`, deleting a transaction that has a receipt will fail. That foreign key also has no covering index.

## F. Warranty Tracker review

**Database:**
- Each product is its own row, linked to a receipt. `expiration_date` is a stored generated column: the override date if one is set, otherwise start date plus N months (years × 12).
- Constraints mirror the frontend validation exactly.
- All four RLS policies check ownership of the warranty **and** the linked receipt. The update policy checks both the old row and the new one.
- Column-level grants prevent changing `user_id`, `expiration_date` or the timestamps. TRUNCATE and anonymous access are revoked.
- A trigger function maintains the timestamps (`SECURITY INVOKER`, empty `search_path`).

**Frontend:**
- Calendar math clamps to the end of the month the same way Postgres does (confirmed with PGlite tests).
- Status: Expired if under 0 days left, Expiring soon for 0–30 days, otherwise Active. It refreshes every 30 seconds and when the tab becomes visible.
- Warranties can be added while uploading a receipt (several products, start date follows the purchase date until edited) or from Warranties → Add, choosing an existing receipt.
- A retry reads back what's already stored, so a failed save doesn't create duplicates or repeat the expense.
- Receipt deletion fetches the warranty count first and refuses to continue if it can't be checked.

**Was the migration applied?** The docs say yes, and the migration file matches the approved SQL. The live database couldn't be checked because it's paused.

**Gaps:**
1. Editing a transaction that has a receipt doesn't update the receipt's merchant, date or total, so warranty "Purchased" dates go stale.
2. Receipt delete removes the file before the database row, so a failed row delete leaves a row pointing at a missing file.
3. No reminders yet (intended).
4. The receipt filter stays set when you navigate away and come back.

## J. Known issues and technical debt

**Biggest technical debt:** code style. `main.jsx` packs the whole app into about 100 extremely long lines. Next come the missing base-schema migrations and having no router.

**Other issues:** budget UI missing; receipt data goes stale after editing its transaction; receipt behaviour when a transaction is deleted is unverified; `cents()` throwing inside `summarize()` on an invalid stored amount; no password reset; "AI" branding; hardcoded "CLOUD CONNECTED"; header controls on every tab; typography and token gaps.
